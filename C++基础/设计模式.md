
设计模式按照种类分为：创建型、结构型、行为型
1.创建型：单例、工厂方法、抽象工厂、建造者、原型
2.结构型：适配器、桥接、组合、装饰器、外观、享元、代理
3.行为型：责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者


# 创建型

## 简单工厂、工厂方法、抽象工厂

简单工厂是一个工厂类用if-else造不同类；
工厂方法是每个产品配一个工厂子类，由子类决定造哪个类；
抽象工厂是一组工厂方法造一整套配套产品族；

# 行为型

## 观察者模式/**发布-订阅模式**

1. 观察者通常要实现统一接口;
2. 发送者常持有观察者列表

下面用一个**气象站 + 多个显示器**的例子来写: 气象站是“被观察者”，温度变化时通知所有显示器；每个显示器是“观察者”，收到通知后更新自己的显示。
![[Pasted image 20261025163009.png]]![[Pasted image 20261025163029.png]]![[Pasted image 20261025163044.png]]
被观察者数据改变——通知存活的观察者——观察者通过自己的方式更新

关键点：
1. 被观察者持有的是弱指针列表，防止外部销毁了观察者对象而被观察者不知道而访问悬空指针，且弱指针不增加引用计数，观察者销毁时自动失效调用析构，不会阻止对象释放；
2. 观察者继承**`std::enable_shared_from_this`**，如果需要把自己注册到其他地方，可以通过shared_from_this()安全获取shared_ptr;

### 观察者很多，如何优化notify性能

#### 节流、批量、去重
1. 节流：不要每个数据变化都立刻通知，可以用定时器或时间间隔控制，比如每 50～100ms 合并一次；
2. 批量：把多次变化攒成一批，一次通知。比如 `QVector<DataPoint>` 或自定义 `struct` 打包后发射
3. 去重：数据没真正变化时不通知，避免无效刷新
4. 如果是model/view框架下，可以用 `blockSignals(true/false)`阻断信号，减少不必要的中间通知；

#### 容器和遍历优化
1. 用std::vector存观察者或者回调函数，连续内存更利于缓存；
2. 如果观察者按事件类型订阅，可以按事件类型分组，避免每次广播都便利所有观察者；
3. 预分配容器容量，减少扩容

#### 锁优化
多线程环境下，列表需要锁保护，但不在锁里执行回调。
![[Pasted image 20261025174039.png]]

#### 回调函数的写法

1. 槽函数/回调只做状态更新或者数据投递；
2. 耗时工作放到工作线程；
3. UI更新合并到主线程事件循环；
4. 避免在回调里触发新的同步信号，防止递归通知风暴

## 架构层

通过NCP作为核心插件管理系统，提供统一的插件注册接口，负责对插件进行管理。
1. 素材库、工程文件等dll动态库都必须实现**同一套插件接口**，比如：systemReady、systemRun、systemStop；
2. ncp作为管理者通过插件管理器扫描目录（toml）读取配置，`LoadLibrary`加载dll，再调用导出函数创建实例；
3. 新增一个模块时，不需要重新编译主进程，主需要把新的dll放到插件目录即可；

**动态发现的能力**：主程序在启动时，读取插件目录toml或者xml或者json来发现插件dll，然后分别加载；


**模块间通信**：观察者模式，通过sigslot信号绑定+runtime事件总线


**各模块对象创建**：抽象工厂/工厂模式，插件管理器ncp根据配置创建具体实例
